## Goal-first rule

Every task belongs to a confirmed Goal through its milestone
(`ws task set-milestone <KEY> <milestone-id>`). Do not create loose tasks. If no
suitable Goal exists, create or confirm one with `workflow-to-spec` first.

The milestone is the Goal: it groups the tasks and has its own lifecycle,
`planning`, `in-progress`, `completed`, `canceled`. Its description does not
render Markdown, so it holds one short plain-text outcome and `Spec: page <id>`.

The Goal page carries `## Outcome`, `## Scope`, `## Decisions`, `## Notes`,
`## Links`, and `## Log`. `## Outcome` is the destination; `## Scope` is the
boundary (in/out). Goal-level log lines go under `## Log`. Read the page before
every edit because the edit replaces it; `ws page history` and `ws page restore`
undo a bad edit. Link each task to its Goal page (`ws link add <KEY> page:<id>`).

A task description carries `## Subtasks`, `## Acceptance criteria`, and
`## Notes`. Implementation notes and task-level logs are item comments.

## Ideas

An `Idea` item is a raw thought that still needs a grilling session. Ideas are
the only items allowed without a Goal, and a title is enough. Never implement an
Idea directly. Grilling one ends in a new Goal (close the Idea as `Done` with a
comment naming the Goal), a `Task` in an existing Goal (change its type and set
the milestone), `Won't Do` with the reason, or a comment on what is still open.
File out-of-scope discoveries as Ideas, naming the originating task.

## Statuses

The item status is the work-state source of truth. Never encode work state in
labels.

| Meaning | Windshift status |
|---|---|
| open | `Open` |
| in progress | `In Progress` |
| awaiting acceptance | `In Review` |
| waiting on a person or information | `Blocked` (say what in a comment) |
| deliberately parked | `On Hold` |
| planned for later | `Open` with a start date (`--start-date`) |
| done | `Done` |
| closed without doing, or superseded | `Won't Do` |

## Routing and labels

- **Agent-ready:** the label `agent-ready` on an unassigned item.
- **Human-ready:** assigned to a person. Never assign items to the agent user.
- **Untriaged:** neither of the above.
- **Work type:** an unlabelled item is an implementation task. Label only the
  exceptions with exactly one of `research`, `prototype`, or `grilling`.

Record the working agent in the custom fields `agent` (id 1, select:
`claude-code` = 1, `codex` = 2, `pi` = 3) and `agent session` (id 2, text), plus a session comment. Set the session field only when the harness provides an ID; never invent one.

Blocked tasks have no `agent-ready` label. At hand-back, remove `agent-ready` and assign Korneel for acceptance.
For work without a PR, move the item to `In Review` explicitly. For PR work,
let the automations below handle status transitions.

## Blocking edges

A task that waits for another task keeps its status and carries a link:

```bash
ws link add <BLOCKED-KEY> <BLOCKER-KEY> --type "Depends On"
```

Do not also mark it `Blocked`; unfinished links already keep it off the work
frontier.

## Repo conventions that workflow skills depend on

- Main branch: `main`.
- Task branches: `feature/<KEY>-<slug>`, for example `feature/WCORE-12-short-slug`,
  the same name Windshift's "Create Branch" dialog proposes but with the key
  UPPERCASE so Windshift links it. The workflow skills' `ws-branch-name.sh`
  prints it. End commit messages with `Refs: <KEY>`.
- Tracker exception: TNT projects use Shortcut; this repository uses Windshift.
